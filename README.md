# 藏语词汇录入与 Word 导出工具

一个跑在本机的中文 Web 应用：按**音节 / 组件**录入藏语词汇，保存到本地 SQLite，
再按**顺序**或**乱序**导出成 Word 文档，用来背单词或做自测卷。

藏文不是简单地按界面顺序拼字符串——本工具实现了一套完整的音节合成器，
会按藏文的 Unicode 组合规则把 7 个组件正确地拼成藏文（见
[藏文音节合成规则](#藏文音节合成规则)）。

> 另有配套的[单文件记忆工具](#配套单文件记忆工具memorize)（`memorize/index.html`）：
> 双击即用、零依赖，用软键盘练汉译藏 / 藏译汉，并把进度存在浏览器里。
> 词库由本工程导出，用 `memorize/update_wordbank.py` 一键灌进去。

## 功能一览

| 模块 | 说明 |
|---|---|
| 词条管理 | 新增、编辑、删除、清空；按藏文 / 释义 / 备注 / 标签模糊搜索；按标签筛选；四种排序 |
| 藏文录入 | 每个音节 7 个下拉框（前加字、上加字、基字、下加字、元音、后加字、再后加字），其中**下加字可以叠多层**；词尾可加 `།`（ཤད）；可增删音节；实时预览合成结果 |
| 合法性提示 | 拼出不合正字法的常见组合时给黄色警告，但**不阻止保存** |
| Word 导出 | **分栏排版**（默认横向 A4、3 栏，可调 2/3/4 栏）或两列表格；顺序 / 乱序、包含 / 隐藏释义、自定义标题、可选随机种子；页脚页码；藏文 run 写入复杂文本字体与 `w:szCs` |
| 数据备份 | 整个词库导出为 JSON，支持「追加合并」与「清空后覆盖」两种导入方式 |
| 测试 | 290 个 pytest 用例，覆盖合成规则、多层下加字、数据层、导出行为与全部 HTTP 路由 |

## 环境要求

- Python 3.11 或更高（开发与验证环境为 Python 3.13）
- 无需数据库服务，数据就是一个 SQLite 文件

## 安装

```bash
cd zwjy

# 建议先建虚拟环境
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements.txt
```

## 启动

```bash
python app.py
```

浏览器打开 **http://127.0.0.1:8000** 即可。

常用参数：

```bash
python app.py --port 9000        # 换端口
python app.py --host 0.0.0.0     # 允许局域网内其它设备访问（默认只监听本机）
python app.py --reload           # 开发模式，改代码自动重启
```

数据库文件在 `data/words.db`，首次启动自动创建。想换位置就设环境变量：

```bash
ZWJY_DB=/path/to/my.db python app.py
```

## 使用说明

### 1. 词条管理

首页就是词条列表。顶部是搜索框，可以：

- **关键字搜索**：同时匹配藏文、释义、备注、标签。搜索词里的 `%` 和 `_`
  会按字面匹配（不会被当成 SQL 通配符）
- **标签筛选**：下拉选择已有标签
- **排序**：创建时间新→旧（默认）／旧→新／更新时间近→远／按藏文
  （最后一项是按 Unicode 码点排序，不是传统藏文词典序，见[已知限制](#已知限制)）

每行右侧有「编辑」「删除」，左上角的复选框用来批量选中后导出。

### 2. 藏文组件录入（重点）

新增 / 编辑页面左侧是**音节卡片**，一张卡片就是一个音节。每张卡片里有 7 个下拉框：

| 组件 | 藏文名 | 可选值 | 说明 |
|---|---|---|---|
| 前加字 | སྔོན་འཇུག | ག ད བ མ འ | 可以留空 |
| 上加字 | མགོ་ཅན | ར ལ ས | 可以留空 |
| **基字** | མིང་གཞི | 30 个辅音 | **必选**，没有「无」选项 |
| 下加字 | འདོགས་ཅན | ཡ ར ལ ཝ ཧ | 可以留空；**可以叠多层**，见下 |
| 元音 | དབྱངས | ི ུ ེ ོ | 可以留空；留空表示**默认元音 a** |
| 后加字 | རྗེས་འཇུག | ག ང ད ན བ མ འ ར ལ ས | 可以留空 |
| 再后加字 | ཡང་འཇུག | ས ད | 可以留空；填了它就必须先填后加字 |

操作要点：

- **「+ 添加音节」** 加一张新卡片；卡片右上角的 **「删除音节」** 删掉它（至少会留一张）
- **下加字可以叠多层**：默认只有一层下拉框，点它下方的 **「+ 加一层」** 才会长出第二层，
  每层右侧的 `×` 用来删掉那一层。层数上限是 3，到顶后按钮自动变灰。
  绝大多数字只需一层，所以界面默认就是一层，和普通录入没有区别
- 所有改动都会触发**实时预览**：右侧大字号显示合成后的藏文，每张卡片下方显示该音节自己的合成结果
- **「音节之间自动用藏文间隔符 ་ 连接」** 默认勾选。取消勾选后，多个音节会直接首尾相连
- **「词尾加 །（ཤད）」** 默认勾选，见[下节](#词尾的-ཤད)
- **组件下拉框的字号开得很大**，为的是把藏文看清。如果你觉得某个下拉框里的字
  被截断了，多半是某项文案太长——选项文案都刻意压到了一个汉字（「无」），
  改动时请保持这一点
- 右侧面板下方显示校验结果：
  - `✕` **红色**：无法合成（比如只选了元音没选基字），保存会被拦下
  - `⚠` **黄色**：组合在藏文正字法里不常见，**不阻止保存**，只是提醒你核对拼写

上面这两个开关都**跟着词条一起保存**，下次编辑会自动回填。

填完点击「保存词条」即可。保存时**服务端会用组件重新合成一次藏文**，
所以「合成藏文」和「组件 JSON」这两份数据永远是一致的。

#### 词尾的 ཤད（།）

`།`（U+0F0D TIBETAN MARK SHAD）本来是**句末标点**，单独一个词并不需要它。
但词汇表、字帖、生词卡这类材料里，词头通常也带一个 ། 作为分隔
（`ཀ། ཁ། ག།` 一路排下去），所以本工具**默认给每个词条都加上**。

- 不需要的词条，在编辑页取消勾选「词尾加 །」即可
- 这个开关跟着词条走，备份里也会保存
- **导入旧备份时不会凭空多出 །**：老数据里没有这个字段，程序会看它原有的藏文
  结尾有没有 ། 来决定开关——不带的保持不带，免得一保存就发现多出来一个标点

### 3. 导出顺序 / 乱序 Word

在列表页按需要选一个入口：

- **导出全部词条**
- **导出当前筛选结果**（带上当前的搜索关键字与标签）
- **导出勾选的词条**（先在左侧勾选，再点这个按钮）

进入导出设置页后可以配置：

| 选项 | 说明 |
|---|---|
| **排版方式** | **分栏**（默认）：像词汇表那样一行一个词条、按栏排下去；**表格**：每行一个词条，左藏文右释义 |
| **栏数** | 仅分栏时生效，可选 2 / 3 / 4，默认 **3 栏** |
| **页面方向** | 默认**横向**。分栏时强烈建议横向——A4 纵向三等分后每栏只有 5.0cm，藏文加释义会挤成一团；横向每栏有 8.4cm |
| 文档标题 | 居中显示，同时成为文件名的一部分；留空则文档里不显示标题。分栏时标题独占整行宽度，不会被挤进第一栏 |
| 导出顺序 | **顺序**＝按录入的先后顺序；**乱序**＝打乱后导出 |
| 随机种子 | 仅乱序时生效。留空＝每次都不一样；填任意数字或文字＝**同样的种子得到完全相同的顺序**，方便导出同一套题做两遍对比 |
| 包含释义 | 勾选＝藏文后面跟释义；取消＝只保留藏文 |
| 隐藏释义 | 需先勾选「包含释义」。勾选后释义留白，打印出来可以自测后再对照 |
| **藏文字号** | 可选 16 / 20 / 24 / 28 磅，默认 **20 磅**（比中文正文大得多，原因见下） |
| 藏文字体 | 写入 Word 的复杂文本字体，默认 `Microsoft Himalaya` |

**藏文为什么默认又大又粗**：藏文字体为了把三四层高的辅音堆叠（`སྒྲུབས` 这种）
塞进一个字身，单个基字只占字身的四成左右。所以同样写 12 磅，中文是正常大小，
藏文看着只有 5 磅左右，打印出来就是一片发虚的小点。因此导出时藏文单独用一个
**明显更大、并且加粗**的字号——藏文字体大多没有真正的粗体字重，Word 会做合成加粗，
效果是笔画更实，正是打印需要的。

按 A4 横向 3 栏算，每栏约 8.4cm、能排 20 行上下，一页大约能放下 60 个词条。

分栏排版里每个词条是一个段落：**藏文 + 制表符 + 释义**。制表位会随栏宽自适应
（栏越窄越靠左），并且配了悬挂缩进——释义太长换行时会和上一行释义左对齐，
不会缩回藏文底下。两种排版用的是同一个藏文字号。

导出的文件名形如：

```
藏语词汇 2026-09-27_顺序_20260927.docx
藏语词汇 2026-09-27_乱序_20260927.docx
```

两种排版都带页脚「第 X 页 / 共 Y 页」；表格排版的行高已加大，方便打印后手写注记。

### 4. 数据备份与迁移

- **备份 JSON**：导航栏上的「备份 JSON」，下载整个词库（含每个词的音节组件）
- **导入**：首页底部「备份导入」面板，两种模式
  - **追加合并**：保留现有数据，跳过藏文+释义完全相同的重复项
  - **清空后覆盖**：先清空全部词条再导入，适合从其它机器整体迁移

导入是**原子**的：程序会先把整个文件解析完，确认没问题才动数据库，
删除与写入在同一个事务里完成。所以文件里哪怕有一条坏数据，结果也是
「一条都没导入 + 词库原样不动」，绝不会出现「词库被清空、只导入一半」。
报错会指明是第几条记录出的问题。

另外，选了「清空后覆盖」但文件里**一条能用的记录都没有**时，导入会被拒绝
而不是把词库清空——拿错文件是最容易犯的错，而真想清空有专门的按钮。
（显式给一个空的 `words: []` 仍然会清空，那是一个明确的意图。）

示例数据和备份文件是**同一种格式**（有测试钉死这一点），可以互相参考着改。
旧版本导出的备份也能直接导入，见[备份格式与版本](#备份格式与版本)。

**没有音节组件的词条也能编辑。** 从别处导入的纯藏文数据没有组件可供回填，
这种情况下编辑页会多出一个直接输入藏文的框，改完保存即可；
如果你改用了音节卡片录入，则以卡片的合成结果为准。

## 藏文音节合成规则

这是本项目最核心也最容易写错的部分，单独说明一下。

### 语义顺序 ≠ 输出顺序

界面上的 7 个组件是按**语义顺序**排的：

```
前加字 + 上加字 + 基字 + 下加字 + 元音 + 后加字 + 再后加字
```

但真正写进 Unicode 字符时，只有**上加字**会造成形式变化：

| 情况 | 输出 |
|---|---|
| 前加字 | 正常辅音形式，原样输出。例：`བ` |
| **有**上加字 | `上加字正常形式` + `基字的下加形式`。例：`ས` + `ཀ` → `སྐ` |
| **没有**上加字 | `基字正常形式`。例：`ཀ` |
| 下加字 | 录入时选正常形式，输出时换成下加形式。例：`ཡ` → `ྱ`，`ར` → `ྲ`。多层则按顺序依次追加 |
| 元音 | 追加在整个辅音堆叠（基字或其下加形式 + 下加字）之后。留空＝默认元音 a，不输出字符 |
| 后加字 / 再后加字 | 正常辅音形式，原样输出 |

### 三个例子

| 组件 | 合成结果 |
|---|---|
| 基字 `ཀ` + 元音 `ི` + 后加字 `ག` | `ཀིག` |
| 上加字 `ས` + 基字 `ཀ` + 元音 `ུ` | `སྐུ` |
| 前加字 `བ` + 上加字 `ས` + 基字 `ག` + 下加字 `ར` + 元音 `ུ` + 后加字 `བ` + 再后加字 `ས` | `བསྒྲུབས` |

第三个例子的字符序列是 `བ ས ྒ ྲ ུ བ ས`（`ག` 因为有上加字 `ས`，换成了下加形式的 `ྒ`）。

### 词尾的 ཤད（།）

合成的最后一步（如果勾了「词尾加 །」）：

```
音节1 ་ 音节2 ་ … ་ 音节N །
```

三个注意点：

- **一个音节都没合成出来时不加**，否则会得到一个只有标点、没有内容的空词
- **། 是排版开关，不是音节组件**——它不参与校验，也不会被当成前加字/后加字
- 已经以 ། 结尾的文本再次保存不会变成 `།།`：直接输入藏文那条路径上是
  「先去掉结尾已有的 ། 再补一个」

### 多层下加字

一个音节最多只有一个**下加字本体**（`ྱ` `ྲ` `ླ` `ྷ`），此外还可以再跟一个 `ྭ`（wa-zur）。
所有已证实的双下加字词形都符合这个结构：

| 词形 | 组件 | 字符序列 |
|---|---|---|
| `གྲྭ` 寺院、僧团 | 基字 `ག` + 下加字 `ར` + 下加字 `ཝ` | `U+0F42 U+0FB2 U+0FAD` |
| `དྲྭ` 网（`དྲྭ་བ` = 网子、网络） | 基字 `ད` + 下加字 `ར` + 下加字 `ཝ` | `U+0F51 U+0FB2 U+0FAD` |
| `ཕྱྭ` 预兆、福运 | 基字 `ཕ` + 下加字 `ཡ` + 下加字 `ཝ` | `U+0F55 U+0FB1 U+0FAD` |

更多的层数只出现在梵文转写文本里（例如 `ཧྐྵྨླྺྼྻྂ` 那种极高的堆叠），
工具允许叠到 3 层并给出提示。

> **关于这里的校验规则**：早期版本写死了一份「本土只有 `གྲྭ` 与 `ཕྱྭ` 两类」的白名单，
> **那是错的**——`དྲྭ་བ`（网）就是个常用词，白名单会把这么常见的词误报成「极为罕见」。
> 与其继续维护一份永远可能不全的枚举，现在改成按**结构**判：
> 第二层必须是 `ྭ`，第一层必须是有据可查的 `ྲ` 或 `ྱ`；**不锁基字**，
> 这样才不会有漏网的词被误报。
>
> 代价是像 `ཧྲྭ` 这种并不存在的拼法也不会被提示——这是刻意换来的：
> 排除错的比纳入错的代价大得多。

编码上不需要特殊处理：藏文区块里**所有下加字母的 `Canonical_Combining_Class` 都是 0**，
不参与规范重排序，所以「基字 + 按录入顺序排列的下加字」直接拼接就是正确的编码顺序。

需要特别说明的是，第二个下加字用的是**普通下加形式**（`ྭ` U+0FAD），
而不是 Unicode 里那组「固定形式」（`ྺ` U+0FBA / `ྻ` U+0FBB / `ྼ` U+0FBC）。
后者按 Unicode 标准的说明**只用于梵文转写与音译**，普通藏文文本不用。测试里对字节序列有断言。

### 映射表怎么来的

正常辅音与下加形式在 Unicode 藏文区块里保持**固定的 `0x50` 偏移**：

```
ཀ U+0F40  →  ྐ U+0F90
ག U+0F42  →  ྒ U+0F92
ན U+0F53  →  ྣ U+0FA3
```

所以代码里没有手抄 30 组映射（抄错一个字符就会生成看起来对、实际错的藏文），
而是用偏移量生成，并由单元测试逐条校验取值范围与抽样结果。

### 关于 Unicode 规范顺序

藏文区块里所有下加字母的 `Canonical_Combining_Class` 都是 0（不参与规范重排序），
而四个元音符号 `ི/ུ/ེ/ོ` 的组合类互不相同。因此按上面的规则拼接出来的字符串
天然满足 Unicode 规范顺序，不需要额外调用 `unicodedata.normalize()`。
测试里对此有断言。

### 两种间隔符：`་` 和 `༌`

藏文里有两个长得几乎一样、但码点不同的间隔符：

| 字符 | 码点 | 用途 |
|---|---|---|
| `་` tsheg | **U+0F0B** | 标准的音节分隔符，本工具始终输出这一个 |
| `༌` tsheg bstar | **U+0F0C** | 特殊排版场合（如行末不断行）；Unicode 里它的兼容分解就是 U+0F0B |

从网页、PDF 或旧文档里复制藏文时经常会把 `༌`（U+0F0C）带进来。
两者渲染结果一样，但码点不同，直接用会「明明库里有这个词却搜不到」。

所以工具在**保存**和**搜索**时都会做一次归一：`normalize_text()` 把 U+0F0C
换成 U+0F0B 再走一遍 NFC 规范化。从别处粘进来的藏文可以直接搜，不用手工替换。

### 合法性校验的尺度

校验用的是一套**常用搭配规则集**（前加字×基字、上加字×基字、下加字×基字、
再后加字×后加字，以及「འ / ཨ 通常不加前后加缀」这类约定），
`tibetan.py` 顶部有明确说明。它的定位是**提示**而不是**判定**：

- 全都是警告，不会阻止保存
- 罕用但正确的组合可能被提示为「不常见」
- 这是刻意的取舍：宁可提示得保守一点，也不要误报

多层下加字按**结构**判，不锁基字（原因见上文）：

- 第二层不是 `ྭ`（wa-zur）时提示「极为罕见」
- 第一层是 `ླ` / `ྷ` 等无据可查的字母、第二层又叠 `ྭ` 时提示
- 三层及以上提示「只出现在梵文转写中」
- 同一个下加字重复叠（比如 `ར` + `ར`）会提示
- 上加字 + 两层下加字构成四层堆叠时会提示

## 配套：单文件记忆工具（memorize/）

除了上面这个录入 + 导出的 Web 应用，工程里还有一个**独立的单文件记忆工具**
`memorize/index.html`：双击就能用，不需要 Python、不需要联网、不需要起服务。

它跟主工程的关系是「主工程负责收集和整理词库，它负责背诵」——
词库用主工程导出成 JSON，再用一个小脚本灌进去。

| | 主工程（`python app.py`） | 记忆工具（`memorize/index.html`） |
|---|---|---|
| 用途 | 录入、编辑、检索、导出 Word | 背单词、复习、看进度 |
| 形态 | 本地 Web 应用，要起服务 | 单个 HTML 文件，双击即用 |
| 数据 | SQLite（`data/words.db`） | 词库内嵌在 HTML 里，进度存在浏览器 localStorage |
| 依赖 | Python + 几个库 | 零依赖 |

### 怎么背

两种模式：

- **汉译藏**：给出中文，用**内嵌的藏语软键盘**拼出藏文。软键盘按组件分组
  （基字 / 元音 / 下加字 / 上加字 / 后加字 / 前加字 / 再后加字，按实际使用频率排序），
  点选后**自动按藏文规则合成音节**——用户不可能拼出错的字符序列，这是它降低门槛的关键。
  提交后自动判分，答错会逐字标出对不上的地方。
- **藏译汉**：给出藏文，**输入中文意思**，自动判分。

  中文没法要求逐字一致——「腹、肚、腹部」你写「肚子」当然算对。所以判分放宽：
  先去掉括号里的词性标注（`（动）`、`（现、未）`），再按逗号顿号分号拆成若干
  「可接受答案」，然后：

  | 情形 | 判定 |
  |---|---|
  | 完全一样 | 对 |
  | 你写的**包含**某个答案（多写了几个字） | 对 |
  | 某个答案**包含**你写的，且你写了 ≥ 2 个字 | 对 |

  太宽松的边界也钉死了：「病、痛（动）」写个「动」不算对（那是词性不是释义），
  「菱形孔格花纹」写个「花」也不算（只写一个字太零碎）。
  真被误判了，反馈里有一个「**其实我答对了**」可以改判——中文近义词没法穷举，
  判严了只会让人烦躁，所以留一个出口。

复习调度：**答错的词排回队尾**，一轮里反复出现直到全对；可以单独刷错词本。
统计：总体进度、正确率、按课（标签）的掌握度、错词表。连对 2 次算「已掌握」。

进度存在浏览器 localStorage 里，**按词条的藏文内容编号**，所以：

- 插新词、删旧词都不会影响其它词的进度
- 订正释义也不会丢进度
- 但**改了一个词的藏文写法就等于换了一个词**，它的进度会重置（更新工具会在报告里点出来）

存储键是 `zwjy-memory:v1:<词库名>`，词库名由更新工具写进 HTML 的
`data-bank-id`（默认取词库文件名，可以用 `--bank-id` 指定）。
**这一条在托管到 GitHub Pages 之后是必须的**：localStorage 按「源」隔离、
不区分路径，而 `https://用户名.github.io/词库A/` 和 `https://用户名.github.io/词库B/`
属于同一个源——键名不带词库名的话，两套词库的进度会串在一起。
换词库名前请想清楚：换了名字，已有的进度就对不上了（等于从头开始）。

### 怎么更新词库

词库变了（增删改）之后，用主工程**重新导出一份 JSON**，然后跑一次：

```bash
cd memorize
python update_wordbank.py 新的词库.json
```

它会：

1. 读入 JSON，归一化成内嵌格式（**兼容两种写法**：本工程导出的备份，
   以及 `要求.md` 里那种中文键名的扁平写法——后者的下加字是下加形式 `ྲ`，
   会自动换算回正常形式 `ར`）；
2. 用 `tibetan.py` 的合成器**逐条校验**「组件能不能合成出这个词的藏文」，
   对不上就报错退出、**一个字节都不改**（防止把半截数据写进去）；
3. 原子替换 `index.html` 里的词库；
4. 打印新增 / 删除 / 内容改动 / **藏文改写**（后者进度会重置，单独列出来）。

其他用法：

```bash
python update_wordbank.py 新词库.json --check    # 只检查，不动文件
python update_wordbank.py 新词库.json --fix      # 组件与藏文对不上时，以组件为准修正
python update_wordbank.py 新词库.json -o 别的.html
```

几个细节：

- **id 由藏文内容算出**（不是数组下标），所以增删词不会让别人的进度错位
- 词库里出现两个一模一样的藏文时，才把释义也算进 id
- 词条内容里万一有 `</script>`，写进去时会转义，不会把 HTML 标签提前闭合
- Windows 默认控制台是 GBK、印不出藏文，脚本会自动降级成「只报数量」而不是崩掉

### 换一份词库

想背别的词库（比如期末词汇），直接导出新 JSON 再跑一次 `update_wordbank.py` 即可——
`index.html` 里只换词库那一段，程序本身不动。要保留两套词库就复制一份 HTML 分别更新，
并用 `--bank-id` 给它们各自起个名字（否则进度会串）。

### 托管到 GitHub Pages

单文件 HTML 天生适合 GitHub Pages，没有构建步骤、没有后端、没有跨域问题。
几个注意事项：

1. **文件名要是 `index.html`**，放在仓库根目录（或用 `docs/` 目录并在设置里指定）。
2. **可以把 `memorize/` 当作一个独立仓库推上去**——它只依赖这两个文件，
   不需要主工程。`update_wordbank.py` 只需要主工程的 `tibetan.py` 来校验，
   不想带的话也可以只推 HTML。
3. **本地打开和线上打开是两套进度。** `file://` 的源和 `https://用户名.github.io`
   是两个不同的源，localStorage 互不相通。以后主要在线上用，就固定用线上。
4. **同一个账号下的多个词库共享 localStorage 命名空间**，所以必须用
   `--bank-id` 区分（见上文）。
5. **换设备 / 清浏览器数据 = 进度丢失。** 进度只在那一台浏览器里。
6. **HTML 会被浏览器缓存**，更新之后如果看着没变，先 Ctrl+F5 强刷。
   GitHub Pages 自己的缓存一般 10 分钟。
7. 词库是内嵌的，所以**改词库 = 改 HTML = 一次 commit**。
   JSON 是按字段换行的，改动只会体现在相应那几行上，diff 很小、看得清。

## 已知限制

诚实地列一下这个工具做不到的事：

1. **下加字最多叠 3 层**，够覆盖本土词汇（最多 2 层）和常见梵文转写；再高的堆叠
   （如 `ཧྐྵྨླྺྼྻྂ`）录不进来。
2. **基字只收录 30 个常用辅音**，不含梵文转写用的 `ཊ ཋ ཌ ཎ ཥ` 等；
   下加字也不含 `ྵ`(SSA)、`ྺ/ྻ/ྼ`（固定形式）这几个梵文转写专用字符。
3. **元音只支持 `ི ུ ེ ོ` 和默认元音 a**，不含 `ཱ`(AA)、`ཻ`、`ཽ` 等
   主要用于梵文转写的符号，也不支持 `ཾ` `ྃ` 这类上加的鼻音符号。
4. **合法性校验不是完整的正字法校验器**，只是常用搭配规则集（详见上文）。
   它可能漏报，也可能把罕用但正确的组合标成「不常见」。
5. **Word 里只导出藏文和释义两列**，备注和标签不会写进文档。
6. **释义是纯文本**，不支持加粗、多义项编号、例句分行等富文本排版。
7. **藏文能否显示取决于字体是否安装。** 导出时写入的是字体名，电脑上没装
   `Microsoft Himalaya`（Windows 自带）就会由 Word 回退到别的字体，
   可能在 Linux / macOS 上显示效果不理想——可以改选 `Noto Sans Tibetan` 或 `Jomolhari`。
8. **单用户工具**：没有登录、权限、并发控制，默认只监听 `127.0.0.1`。
   如果要用 `--host 0.0.0.0` 开放给局域网，请自行意识到**任何人都能读写你的词库**。
9. **SQLite 单文件**：不适合多个进程同时写入。同时开两个 `python app.py` 指向同一个
   数据库文件可能出现锁冲突。
10. **没有回收站**：删除和「清空全部词条」不可撤销，操作前建议先导出一份 JSON 备份。
11. **「按藏文」排序是 Unicode 码点序，不是传统藏文词典序。** 藏文词典按**基字**
    归类，排序时要忽略前加字与上加字（例如 `བསྒྲུབས` 应排在 `ག` 那一类），
    还要处理同字不同形的情况；这套排序键没有实现。目前用「按藏文」排序只适合
    把相同的词聚在一起，不要当成词典顺序用。
12. **搜索是子串匹配，不理解藏文的音节边界。** 搜「`བོད`」会命中所有含该子串的
    词条，包括它是别的词的组成部分的情况。

## 备份格式与版本

备份文件（以及 `data/sample_words.json`）的形状是：

```jsonc
{
  "format": "zwjy-tibetan-vocabulary",
  "version": 2,                      // 外层备份格式版本
  "exported_at": "2026-09-27 23:00:00",
  "count": 33,
  "words": [
    {
      "tibetan": "དྲྭ་བ",
      "components": {                // v2 起是**对象**，可以直接手改
        "version": 2,                // 组件结构版本（与外层版本是两回事）
        "auto_join": true,           // 音节之间是否用 ་ 连接
        "trailing_shad": true,       // 词尾是否加 །
        "syllables": [
          { "prefix": "", "superscript": "", "root": "ད",
            "subjoined": ["ར", "ཝ"], "vowel": "", "suffix": "", "suffix2": "" },
          { "prefix": "", "superscript": "", "root": "བ",
            "subjoined": [], "vowel": "", "suffix": "", "suffix2": "" }
        ]
      },
      "meaning": "网子；网络",
      "note": "",
      "tags": ["名词", "双下加字", "多音节"],
      "auto_join": true,
      "created_at": "2026-01-01 09:32:00",
      "updated_at": "2026-01-01 09:32:00"
    }
  ]
}
```

两个版本号含义不同：

- **外层 `version`**（备份格式）：v1 时每条记录的 `components` 是**内嵌的 JSON
  字符串**（转义嵌套，很难手改）；v2 起改成**对象**，与示例数据同形
- **组件 `version`**：v1 时 `subjoined` 是字符串（一个音节只能有一个下加字）；
  v2 起是**字符串列表**，支持多层下加字

**两种旧写法都能直接导入，不需要手工转换**（见 `models._word_from_backup`）：

| 旧写法（v1 / 老数据） | 新写法（v2） |
|---|---|
| `"components": "{\"syllables\": [...]}"` | `"components": { "syllables": [...] }` |
| `"subjoined": "ར"` | `"subjoined": ["ར"]` |
| 没有 `trailing_shad` 字段 | `"trailing_shad": true` |

最后一行的处理值得说明：老数据里没有 `trailing_shad` 时，程序**按它自己的藏文
推断**——结尾带 ། 的算开、不带的算关，而不是一律套用默认值。
这样导入旧备份不会凭空多出一个标点。显式写了这个字段的以字段为准。

重新导出时统一写成 v2。备份里**不含 `id`**——id 是本地数据库的自增值，
导入时会被重新分配，写进备份反而容易让人以为能靠它找回原编号。
